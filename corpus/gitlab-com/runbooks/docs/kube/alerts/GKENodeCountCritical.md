# GKENodeCountCritical

> [!note]
> This playbook covers the `component_saturation_slo_out_of_bounds:kube_pool_max_nodes` saturation alert. The name `GKENodeCountCritical` is a historical anchor; a single saturation alert fires on the hard SLO (95%). The soft threshold (90%) is diagnostic only — see [Soft threshold (90%)](#soft-threshold-90) below.

## Overview

A GKE node pool has reached or is about to reach its configured maximum number of nodes (`max_node_count` in Terraform). Cluster Autoscaler cannot add more nodes to that pool until the cap is raised.

The limit is per-zone. For a zonal cluster the number of nodes equals the cap; for a regional cluster the cap is multiplied by the number of zones the cluster spans.

## Metrics

- SLI: `gitlab_component_saturation:ratio{component="kube_pool_max_nodes"}`
- Soft SLO: 90%. Hard SLO: 95% (alert fires above hard).
- Dashboard: [Kube pool max nodes saturation](https://dashboards.gitlab.net/d/alerts-sat_kube_pool_max_nodes/)
- Node pool caps live in [`config-mgmt`](https://ops.gitlab.net/gitlab-com/gl-infra/config-mgmt/) — see the `gke_nodepool_max_nodes` variable in each environment's `variables.tf` (for example [`environments/gprd/variables.tf`](https://ops.gitlab.net/gitlab-com/gl-infra/config-mgmt/-/blob/main/environments/gprd/variables.tf)) and its use in `gke-regional.tf` / `gke-zonal.tf`. The caps are exported to Prometheus as `terraform_report_google_cluster_node_pool_max_node_count` via a [CI job on Terraform runs](https://ops.gitlab.net/gitlab-com/gl-infra/config-mgmt/-/blob/main/.gitlab/ci/terraform.gitlab-ci.yml).

## Alert Behavior

- Severity `s3`.
- Scope silences to `(cluster, label_pool)`.

## Severities

- `S2` when workload pods are pending due to lack of capacity — see [`KubeSchedulingFailures`](KubeSchedulingFailures.md) firing on the same cluster.
- `S3` when at cap but scheduling is not currently failing.

## Verification

1. Identify the affected pool. The alert labels include `cluster`, `label_pool`, and `shard`:

    ```sh
    gcloud --project <PROJECT> container node-pools list \
      --cluster <CLUSTER> --location <LOCATION>
    ```

2. Cross-check the Cluster Autoscaler status:

    ```sh
    kubectl describe configmap cluster-autoscaler-status -n kube-system
    ```

    Look for a node group where `cloudProviderTarget == maxSize`.

3. Confirm the Terraform-reported cap matches the GKE-side cap. Divergence means Terraform hasn't run since the last change.

## Troubleshooting

1. Check pending pods and their reasons — see [`KubeSchedulingFailures`](KubeSchedulingFailures.md).
2. If the pool has been at cap and the workload is healthy, raise `gke_nodepool_max_nodes` for the relevant pool in `config-mgmt`. Apply via Atlantis.
3. Before raising, verify:
   - The cluster subnet has enough IPs. `maxSize` cannot exceed the number of IPs in the pod CIDR range. Follow [k8s-operations.md — Add a secondary pod IP range](../k8s-operations.md#add-a-secondary-pod-ip-range) if the subnet is the binding limit.
   - GCP quota (CPUs, in-use IPs, disk types, instance group size) allows more nodes.
4. If the cap is high enough but new nodes fail to come up, follow the `scale.up.error.*` diagnostics in [`KubeSchedulingFailures`](KubeSchedulingFailures.md#top-causes-we-have-seen-in-production).

## Possible resolutions

- Raise `gke_nodepool_max_nodes` for the pool via a `config-mgmt` MR + Atlantis apply.
- Rebalance workloads onto a different pool with headroom.
- Right-size the workload's resource requests if they are inflated.

## Soft threshold (90%)

The `kube_pool_max_nodes` saturation SLI has a soft threshold at 90% in addition to the hard 95% threshold that fires this alert. Only the hard threshold produces a firing alert; the soft threshold is a dashboard signal for pools trending toward the cap.

- SLI: same as the paging alert — `gitlab_component_saturation:ratio{component="kube_pool_max_nodes"}`.
- Longer-term trend:

    ```promql
    count(stackdriver_gce_instance_compute_googleapis_com_instance_uptime{instance_name=~"gke-gprd.*"})
    ```

- Break down saturation by pool from the [Kube pool max nodes saturation dashboard](https://dashboards.gitlab.net/d/alerts-sat_kube_pool_max_nodes/) to spot pools sitting consistently above 90%. Treat these as candidates for a proactive cap raise, workload rebalance, or right-sizing before they hit the hard threshold.
